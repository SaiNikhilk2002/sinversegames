# Deployment

SinverseGames runs on three services:

| Piece | Host | How | Cost* |
| --- | --- | --- | --- |
| Web app (`apps/web`, Next.js 16) | **Cloudflare Workers** | `@opennextjs/cloudflare` adapter, built by Workers Builds | **Workers Paid, $5/mo** (see "Why Workers Paid") |
| Realtime server (`apps/realtime`, Socket.IO) | **Railway** | One always-on service from `apps/realtime/Dockerfile` (`railway.json`) | Usage-based; a small always-on Node service is typically ~$5/mo |
| PostgreSQL | **Neon** | Pooled connection string | Free tier to start |
| DNS / TLS | **Cloudflare** | Existing zone | Free |

\*Check current pricing with each provider. No Redis, KV, R2 or Hyperdrive is required.

## Why this split

- **Next.js on Cloudflare: Workers, not Pages.** The app uses server rendering, API routes, server actions, cookies and Prisma. Static Pages export can't do that. The OpenNext adapter runs the full app on Workers. Verified: the production Worker passed all 8 Playwright end-to-end tests in `workerd` (Cloudflare's runtime) against Postgres and the realtime server.
- **Realtime on Railway, not Workers.** The game server keeps rooms, timers and Socket.IO connections in memory for the length of a match. That's what a persistent Railway service is for. Moving it to Workers would mean rewriting it on Durable Objects. That's possible, but it's a rewrite, not a deployment.

### Why Workers Paid

The bundled Worker is about **4.7 MiB gzipped**: Next.js 16, the Prisma query engine (WebAssembly, about 1.1 MiB gzipped, currently included twice) and the OG-image renderer (about 0.5 MiB). The free plan's limit is 3 MiB; Paid allows 10 MiB. Even with the duplicate removed and OG images dropped, the Worker would be about 3.1 MiB, still over the free limit. Workers Paid is $5/month per account and covers all your Workers. If you already have it for other apps, this adds no fixed cost.

## How the Cloudflare build differs from the Node build

`next dev`, `next build` and `next start` work exactly as before. Only the Cloudflare build (`pnpm cf:build` in `apps/web`) changes three things:

1. **Prisma client.** Workers can't compile WebAssembly from bytes at runtime, so `open-next.config.ts` sets `NEXT_BUILD_TARGET=cloudflare`. `next.config.ts` then aliases `#prisma-client` to the `workerd` variant generated by the second generator in `schema.prisma`, which imports the engine as a static wasm module.
2. **Database connections.** On Workers, `getDb()` creates a one-connection client per call instead of a global pool, because Workers tie sockets to the request that opened them.
3. **pg socket shim.** `pg-cloudflare` (pg's Workers TCP adapter) is added to file tracing.

The OpenNext build creates symlinks and **doesn't run on plain Windows**. Use Workers Builds (Linux), CI, or WSL. Normal `pnpm build` works on Windows.

## 1. Secrets

Generate two independent secrets:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"   # AUTH_SECRET
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"   # ADMIN_TOKEN
```

Both must be **identical** on the Worker and on Railway. Never commit them.

## 2. Neon

1. Create a project in the region closest to your Railway region, for example AWS us-east-1 with Railway us-east.
2. Copy the **pooled** connection string. The host contains `-pooler`; keep `?sslmode=require`. This is `DATABASE_URL`.
3. Apply migrations from your machine or CI:
   ```bash
   DATABASE_URL="postgresql://…-pooler…/neondb?sslmode=require" pnpm db:deploy
   ```
   Repeat on every release that adds files under `packages/db/prisma/migrations`.

## 3. Railway: realtime server

Create a **new project** (for example `sinversegames`) so nothing touches your existing projects.

1. **New Service → GitHub Repo →** `SaiNikhilk2002/sinversegames`, branch `main`. Leave Root Directory empty. `railway.json` at the repo root sets everything else:
   - Dockerfile build: `apps/realtime/Dockerfile`
   - health check: `/health`
   - one replica, restart on failure
   - watch paths, so a web-only commit doesn't redeploy the game server
2. **Variables:**
   | Variable | Value |
   | --- | --- |
   | `AUTH_SECRET` | from step 1 |
   | `ADMIN_TOKEN` | from step 1 |
   | `DATABASE_URL` | Neon pooled URL |
   | `ALLOWED_ORIGINS` | `https://<your-domain>` (exact origin, no trailing slash; comma-separate if you add `www`) |

   Railway provides `PORT`, and the image sets `NODE_ENV=production`. The server refuses to start in production without `ALLOWED_ORIGINS`.
3. **Settings → Networking → Generate Domain** (gives `*.up.railway.app`), or **Custom Domain** `rt.<your-domain>` (see step 5).
4. **Check:** `https://rt.<your-domain>/health` returns `{"status":"ok",…}`.

With the CLI instead: `railway login`, `railway init` (new project), then `railway up` from the repo root.

Active matches live in memory, so a redeploy ends games in progress. Players see "The game server restarted"; finished results are already saved. Deploy at quiet times.

## 4. Cloudflare Workers: web app

**Workers & Pages → Create → Import a repository →** `sinversegames`:

| Setting | Value |
| --- | --- |
| Project name | `sinversegames-web` (must match `name` in `apps/web/wrangler.jsonc`) |
| Root directory | `apps/web` |
| Build command | `pnpm cf:build` |
| Deploy command | `npx wrangler deploy` |
| Build variables | `NEXT_PUBLIC_SITE_URL=https://<your-domain>`, `NEXT_PUBLIC_REALTIME_URL=https://rt.<your-domain>`, `NEXT_PUBLIC_BRAND_NAME=SinverseGames`, `NEXT_PUBLIC_SUPPORT_EMAIL=…` |

The Node version comes from `apps/web/.node-version` (24) and pnpm from `packageManager`.

`NEXT_PUBLIC_*` values are **inlined at build time** (including the CSP `connect-src`), so set them as *build* variables and redeploy after changing them.

**Runtime secrets** go under the Worker's *Settings → Variables and Secrets*, as type Secret, or via the CLI:

```bash
cd apps/web
npx wrangler secret put AUTH_SECRET
npx wrangler secret put ADMIN_TOKEN
npx wrangler secret put DATABASE_URL
```

Manual deploy from Linux, macOS or WSL instead of Workers Builds: `pnpm --filter @platform/web cf:deploy`, with the same `NEXT_PUBLIC_*` values in the environment.

Local check in the real Workers runtime (Linux/WSL): put `AUTH_SECRET`, `ADMIN_TOKEN` and `DATABASE_URL` in `apps/web/.dev.vars` (git-ignored), then run `pnpm --filter @platform/web cf:preview`.

## 5. DNS (existing Cloudflare zone)

Add only new records; don't change zone-wide settings such as SSL mode, which your other apps rely on.

- **Site:** in the Worker, open *Settings → Domains & Routes → Add → Custom domain* and enter `<your-domain>` or `games.<your-domain>`. Cloudflare creates the DNS record and certificate. This fails safely if the hostname is already in use.
- **Realtime:** in Railway's *Custom Domain*, enter `rt.<your-domain>`. Then in Cloudflare DNS, add the `CNAME` Railway shows (plus any `_railway-verify` TXT record) with **Proxy status: DNS only (grey cloud)**. Railway issues the TLS certificate. DNS-only keeps WebSockets direct and avoids depending on the zone's SSL mode.

Then make `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_REALTIME_URL` and `ALLOWED_ORIGINS` match these hostnames exactly.

## 7. Launch checklist

- [ ] Workers Paid plan active on the Cloudflare account.
- [ ] Fresh `AUTH_SECRET` and `ADMIN_TOKEN`, identical on the Worker and on Railway.
- [ ] `pnpm db:deploy` run against Neon.
- [ ] Railway: `ALLOWED_ORIGINS` is the exact site origin; `https://rt.<domain>/health` returns ok.
- [ ] `https://<domain>/api/health` returns `{"status":"ok","web":"ok","database":"ok","realtime":"ok"}`.
- [ ] Two browsers can create a room, join by invite link and finish a match. The match then appears on `/profile`.
- [ ] `/admin` sign-in with `ADMIN_TOKEN` shows metrics.
- [ ] Legal pages reviewed; `NEXT_PUBLIC_SUPPORT_EMAIL` is a monitored inbox.
- [ ] Uptime monitoring on both health URLs.
